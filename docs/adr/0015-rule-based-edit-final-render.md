# ADR-0015 — "Tez montaj": rules make the plan, segments + one master make the file, QA reads the file

**Why.** The spec's pipeline after analysis is Director → Editor → Color / Audio / Motion / Captions → QA → Render → Delivery. The Director and Editor are model-driven agents (Phase 6) and wait for a model key; everything after them is deterministic and was already built as engines (Phases 7–8). Without a plan, none of it reaches the owner as a finished video. Talking-head footage — the owner's main material — has a well-known first pass that needs no judgement: keep the speech, cut the pauses, drop unusable shots, put the face in the frame. The VPS has four shared cores and no GPU, and the final render must start from the originals (4K HEVC, HDR, Log), never the 720p proxies.

**Impact.**
*Plan.* `synthcut_timeline.autoedit.build_plan` turns material into a normal `editplan/1`: speech ranges from transcript words (pauses longer than 0.6 s cut, 0.12 s of air around each phrase), shots flagged black / frozen removed, footage without speech contributes the middle 3 s of each usable, non-duplicate shot, a target duration stops on a phrase boundary. Reframing covers the output frame and moves the picture so the largest face sits centred horizontally and at 40 % from the top; a picture more than twice narrower than the frame (vertical phone video in 16:9) is fitted over a blurred copy of itself instead of being cropped to a strip. Each clip carries its automatic grade (`grade/1`, shot-matched across files) as an effect; the plan carries the automatic mix (`mix/1`) and the noise floor in `metadata`. The plan is validated like any agent's plan, stored append-only in `edit_plans` (version unique per project) and the Director stage is marked *skipped* — honestly, no agent decided it. `Transform.x/y` widened from ±1 to ±4 (a vertical crop of wide footage needs ±1.08); old plans stay valid.
*Render.* One FFmpeg run per clip seeks into the original, converts colour to Rec.709 exactly as ingestion did for the proxy (so the grade measured on the proxy fits), places, applies the grade LUT and cuts exactly `round(d·fps)` frames and `d·48000` samples (last frame cloned, sound padded, if the source ends early) into a near-lossless intermediate (x264 `ultrafast` CRF 12 + PCM up to 1080p, `veryfast` for 4K; free scratch space is checked first). The concat demuxer joins them with per-segment durations, so cuts never drift. The motion layer is the Phase 7 Remotion PNG sequence, drawn at ≤ 1920 px and ≤ 30 fps and scaled / time-matched by the overlay. Loudness is measured once over the joined timeline (voice chain + SFX), then one master pass composites, mixes, applies the second `loudnorm` pass and encodes the preset (x264 `veryfast` CRF 18 up to 1080p, CRF 20 for 4K; AAC 192k; BT.709 tags) — and, when the master will probably exceed the bot limit, the chat copy as a second output of the same pass. Memory stays flat however long the timeline; progress is reported per step. Features the renderer does not execute yet (B-roll layers, voice / SFX / library audio tracks, speed changes, transitions, keyframes) are refused with a reason; music beds from uploaded files arrived with ADR-0017, never dropped silently.
*QA.* One decode of the output runs `blackdetect`, `freezedetect`, `ebur128` and `silencedetect`; ffprobe checks size, frame rate, duration, codecs. `qa/1` gives each check pass / warn / fail with an Uzbek message; a failing report blocks delivery.
*Delivery.* `deliver.telegram` (io queue) sends the file with `sendVideo` when it is under the 50 MB bot limit; for larger masters the render job also makes a bit-rate-budgeted copy for the chat, and the full-quality file stays downloadable in the Mini App. One `renders` row per (plan version, preset, kind): a second request re-uses it.

*Measured* (owner's 161.7 s 1080p Display P3 clip → 119.7 s, two shared cores): first render 37 min; wide-gamut matrix moved into the LUT → 30 min (segments 8.2, Remotion 10.4, master 7.7, chat copy 2.7, QA 0.9). Then, from a 20 s benchmark: master `fast` → `veryfast` CRF 18 (70 → 25 s per 20 s, same size class), intermediate `veryfast` → `ultrafast` (38 → 15 s), chat copy in the master pass (+12 s instead of a ~27 s pass). The 8-bit LUT pass stays the main segment cost; FFmpeg's float LUT path is 1.5× faster but its 4:2:0 conversions are measurably worse on colour edges (p99 20–33 vs 10 code values), so it is not used.

**Alternatives.** Rendering from proxies (fast, but 720p and tone-mapped: not a deliverable); one FFmpeg graph with every clip as an input (all decoders open at once — the same memory trap that OOM-killed ingestion); MLT / melt as the renderer (another timeline model to translate into, and no per-step progress); waiting for the Director before shipping any of this (the owner would get no video until a key arrives).

**Decision.** The rule-based editor makes ordinary, validated, versioned plans; the renderer executes any plan in segments plus one master from the originals; QA measures the file; delivery goes through the Bot API from the worker. When the Director arrives it writes plans of the same shape and everything downstream stays.
